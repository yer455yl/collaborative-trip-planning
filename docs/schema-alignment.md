## Role Contract

Persist `owner` and `editor`; display **Organizer** and **Participant**, respectively. Both active roles can read, edit, vote and confirm validated initial plans. Comment, chat and actual-expense permissions below are deferred. Only the organizer manages invitations, membership and ownership. Exactly one active owner must remain. `viewer` is deferred and is not a supported invitation or membership value in this baseline. A future read-only role needs explicit requirements, policies, UI and tests before introduction.

## Constraints and Trusted Transactions

- Retain all same-trip composite foreign keys from the [initial design](database-design.md). `ai_proposals.confirmed_by` must reference an active authorized member of the same trip when confirming. A nullable confirmer is allowed only before confirmation.
- Validate positive traveler count, inclusive dates, language enum and nonempty preference/type values. Treat interest values as a reviewed vocabulary; never interpolate preference text into executable queries.
- Place/event/custom discriminators must match references: place requires place and no event; event requires event and its matching place; custom permits neither. Enforce the event-place pair with a composite reference or a transactional check. Validate event overlap, event status and schedule in the trip time zone; a known canceled event is never eligible.
- `estimated_cost` on an itinerary entry is the normalized whole-party amount in the trip currency. `estimate_basis` records original price, currency, unit, quantity, included dates/nights and source/check date. A post estimate is user content, not verified catalog pricing; require cost and currency together and never use it as a validated budget source. Use exact money; never charge accommodation once per entry and again in a separate total. An accommodation room capacity and night count must be explicit before claiming a complete estimate.
- Keep catalog prices nullable until verified. Reject a valid-budget label if mandatory opening/price/unit/source data is missing or stale under the agreed freshness policy. A source/check date records provenance, not proof that a price will remain valid.
- Invitation tokens are cryptographically random; store only their hashes. Acceptance atomically locks/consumes an unexpired, unrevoked token and creates/reactivates one membership. Concurrent acceptance grants one recipient only; replay by the same accepted recipient returns the existing result. Use a configured expiry and share tokens only over authenticated/secure channels. Tokens must never appear in public logs.
- An AI request key deduplicates retries. A draft is private trip data. `pending` becomes `ready`, `invalid` or `failed`; only a ready, unexpired, validated proposal can be confirmed. The trusted confirmation transaction rechecks actor, trip, membership, base version, catalog and budget, writes itinerary changes, increments the trip version and sets `confirmed`, confirmer/time and applied version together. Retry returns the saved outcome; rejection/expiry/validation failure never changes the confirmed plan. Do not persist secrets or unrestricted provider prompts.
- Published feed reads expose an explicit allowlist: post content, public author display fields and public catalog place data. `trip_id` never grants public access to private records. Media requires approved storage policies, size/type validation and suitable public publication semantics; a private storage URL is not automatically safe to publish.
- Ordinary users may create only their own reports and cannot set disposition/reviewer fields. Only the trusted moderation command can resolve/dismiss reports. Do not store reviewer authority in a user-editable profile or derive it from trip ownership. Moderation actions need access-controlled evidence and a retention policy before production.
